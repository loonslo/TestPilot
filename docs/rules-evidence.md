# 规则出处与参考构建观察

日期：2026-10-15。观察对象：参考构建（衡仓后端 55cf875，本机沙箱，开发配置：关闭 OCR、邮箱登录和任何外部数据源），用 `tools/probe_reference.py` 的固定脚本观察，共 102 步：设了预期状态码的调用全部一致，其余调用的状态码和错误码逐条核对过，结果列在下表。规则全文在 [benchmarks/public/rules.json](../benchmarks/public/rules.json)。

此后规则在参考构建上是否成立，由判定套件（`benchmark verify`）逐条检查，结果在 [acceptance.md](acceptance.md) 的 A2 一节；本文保留写规则时用探针做的观察和出处。

“出处”一列：**文档** = 被测项目自己的 docs/API.md、docs/error-codes.md、README；**业主** = 文档没写，当前内容取自参考实现，需要被测项目的主人（用户）确认是不是想要的产品规则。**2026-10-15 用户确认：下表“业主确认项”共 10 条全部按参考实现**，`rules.json` 里这 10 条带 `confirmed_on`。

## 参考构建与文档不一致或有疑问的地方

这些**不是规则**，没有计入评分；它们是被测项目自己的问题或文档问题，由用户判断是缺陷还是文档过期。都是在开发配置的沙箱里观察到的，不代表线上。

| 编号 | 观察 | 对照 |
| --- | --- | --- |
| D-1 | `ledger.summary` 的 `records.accounts` 和 `accounts` 恒为空数组，即使已有账户 | docs/API.md 的 2026-09-05 账本快照一节写 records 含 accounts |
| D-2 | 同一个 `client_request_id` 换内容重发，返回 409 `VERSION_CONFLICT` | docs/error-codes.md 写的是 `IDEMPOTENCY_CONFLICT` |
| D-3 | 重放一个已成功的交易批次，若其中引用的持仓后来被归档，返回 400 `HOLDING_NOT_FOUND`，而不是首次的响应（引用检查先于重放查找） | 幂等重放通常应返回原响应 |
| D-4 | 从余额为 0 的账户取款 999,999 被接受（200）。`validate_transaction_cash`（会返回 `INSUFFICIENT_FUNDS`）在 v1_api.py 里定义了，但没有任何调用，也没有测试引用 | 要不要禁止透支是产品决定；规则没有覆盖 |
| D-5 | 引用不存在或已归档的持仓返回 400 `HOLDING_NOT_FOUND`，引用不存在的账户返回 404 `NOT_FOUND` | 两类引用的错误风格不一致 |
| D-6 | 被测仓库提交的 `openapi.json` 是旧快照（51 个路径，缺 `/health/version`），运行时导出 52 个；OpenAPI 把校验错误写成 422，实际返回 400 `VALIDATION_ERROR`；所有 200 响应都是无类型的 `SuccessEnvelope` | 公开规格已按实际行为处理 |
