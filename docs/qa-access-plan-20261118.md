# 按测试角色权限设计 TestPilot 接入流程

2026-11-18 · 实施方案

2026-11-18 实施更新：根据用户后续确认，0.1.2 将源码、接口规格和 Git 仓库收进同一网页入口。选择的目录本身是可读的 Git 仓库根目录且有有效 HEAD 时读取提交快照，其余目录读本地文件。文件按内容和扩展名进入现有适配器。下文关于用户显式选择 Git 入口的安排保留为历史方案。实测见 [验收记录](acceptance.md)。

## 需求与现状

测试人员可能拿到接口规范、开发交付的源码目录或压缩包，也可能暂时只有工单。开发可以交付一份源码副本，仓库访问权限和 Git 历史仍由开发团队管理。工作台按实际拿到的资料提供入口，资料未齐时允许保存草稿。

现有任务服务能够从本地 OpenAPI/Swagger 文件或显式 URL 发现接口，支持空草稿及空提交。源码采集当前只能从 Git 提交读取。顶栏的通用浏览入口会把选中的普通目录当作 Git 仓库，请求读取仓库根和 HEAD，失败时报截图所示错误。Git 探测只应出现在显式选择「Git 仓库」时。「本地源码目录」需要单独接入，采集后的文件内容可以由现有静态解析器处理。

安装权限也要单独处理。目前给另一台电脑的主要安装说明要求克隆 TestPilot 私有仓库。项目已有构建和安装 wheel 的历史记录，需要验证由维护者交付安装包后，测试人员能在没有 Git 和私有仓库权限的电脑上安装并启动，从打开软件走到接口清单。

业务执行当前限定到显式 `http://127.0.0.1:<端口>`，回环地址上的测试服务仍需另外准备。测试人员只有共享 QA 地址时，可以先做资料导入和用例设计，但现有执行器无法直连该环境。在线文档导入和业务执行是两个独立权限。

## 角色、权限与任务交接

| 角色或职责 | 实际交付给 TestPilot 的内容 | 能走到哪里 |
| --- | --- | --- |
| 黑盒接口测试人员 | 经授权的 OpenAPI/Swagger 文件或文档地址、工单中已知的测试范围。资料不齐时可先登记项目和任务 | 保存草稿、导入、选范围、设计和修订用例。待环境和审批齐备后执行 |
| 拿到源码副本的测试人员 | 开发交付的可读目录或解压后的源码包，以及本轮获准分析的文件或子目录；交付版本可选 | 从本地副本静态提取接口，查看来源和未解析项。只需该副本的读取权限 |
| 业务规则或接口负责人 | 确认可见接口、发布变更、预期结果和允许使用的测试数据；需要时提供脱敏规范导出 | 补齐测试依据。仅有接口结构时，业务预期保持待确认 |
| 测试环境负责人 | 提供获准执行的测试环境、账号角色或匿名许可、允许操作、合成数据及清理约定 | 确认环境、账号、操作范围与部署身份，供审核和执行使用 |
| 用例审核人 | 人工核对用例修订、预期、环境、账号别名和操作范围，记录批准或暂缓 | 批准范围内的用例可执行。修改修订或执行配置后重新批准 |
| 获授权的开发或技术测试人员 | 可读本地仓库、固定提交、显式源码范围 | 通过高级入口补充源码发现。发布差异分析也由具备相应权限的人执行 |

这些是职责和可用能力，实际可由同一个人承担多项。当前工作台依靠本机会话令牌控制访问，并记录人工审批。组织角色、环境账号和 TestPilot 会话身份是三个独立概念。团队级授权由组织现有机制提供，涉及多人登录和角色校验时须另行设计。

## 流程和状态边界

1. **新建任务。** 填项目名，按拿到的资料选择「接口文档」「本地源码目录」或「稍后补资料」。「接口文档」支持本地文件和在线地址。「本地源码目录」接受普通目录，也接受开发交付包解压后的目录。首版由测试人员解压后选目录，直接导入压缩包另行评估。「Git 仓库」作为独立高级入口，选择后显示仓库、提交和范围。
2. **确认本轮范围。** 记录资料来源、内容哈希和采集时间，再由测试人员选定接口。目录来源记录所选范围和相对路径，并冻结实际读取的内容。文档版本、交付批次、工单或发布号可作为声明信息。清单只覆盖输入范围，实际部署的版本核验单独显示。文档地址需登录时，可由负责人提供授权导出或使用已有文档认证配置。只有需求描述且缺少可解析资料时先保存草稿。
3. **设计并审核用例。** 基于接口资料及经确认的业务规则，可导入用例或按现有模型配置生成。规则缺失的场景需补证据或暂缓。源码副本的本地读取、外发给模型、业务 API 执行分别授权。源码目录发现可纯本地完成；生成时只使用已获准外发的材料，默认给出清单和经选定的依据，原始源码需单独授权。凭据由宿主按账号别名注入。
4. **准备和执行。** 环境未配置、账号未获授权、审批未完成或版本与预期不符时，告诉用户缺什么以及由谁补齐。由现有任务服务复核冻结的用例、环境与操作范围。账号所获权限不足应呈现相应执行证据；如果拒绝访问本来就是这条已审核用例的预期，则按断言判定。缺失执行权限或证据的用例保留为阻塞或未运行。
5. **查看结果与回归。** 报告保留用例修订、测试范围、环境、版本核验状态与请求响应证据。优先复用已批准的测试集；拿到新接口规范或发布说明后，对比接口和业务变化，再按新环境或新修订审核。无源码回归先从人工确认变更范围做起，自动规范差异另排期。

## 本地源码目录的实现边界

- **任务配置。** 为本地源码登记单独的目录根和所选相对范围，保留现有 Git 仓库任务的字段和值。把目录来源与范围纳入任务绑定。采集结果冻结后收到新版交付时，创建新任务，原清单和历史记录仍可追溯。
- **采集与静态解析。** 宿主只读所选根下允许的普通文件，排除敏感路径、隐藏目录、越界链接和 Windows 目录联接，并限制扫描文件数及总量。源文件从授权目录读入后交给现有快照和静态解析流程，整个发现过程无需启动被测服务或导入、安装、执行交付代码。
- **支持范围。** 首版使用现有 Python AST 适配器。遇到 Java、TypeScript 等未支持的源码，显示能力边界，引导选择交付目录里已有的 OpenAPI/Swagger 文件，或向开发索取规范。静态找到的接口来自已扫描资料，动态路由和其他未解析项单独列出。
- **版本与模型。** 内容哈希用于认定本次分析的文件内容，交付版本可以留空，运行环境身份单独核验。核对现有模型材料构建路径，确保新增的目录快照默认留在本地；测试用模型替身断言请求中仅包含获准材料。

## 实施顺序与验收

| 工作包 | 实现范围与依赖 | 可观察的验收结果 |
| --- | --- | --- |
| P0 · 无 Git 安装与主流程 | 验证维护者通过内部渠道交付 wheel 和锁定依赖的安装方式。调整网页的新建、资料表单和顶栏浏览入口，复用现有任务创建、配置与发现接口。仅从显式仓库选择入口请求 `/api/fs/list?git=1`；保留现有仓库任务的回填和只读检查。快速上手及安装演示使用无提交的合成文档 | 在 Git 不可用、没有被测仓库、没有模型和环境账号的 Windows 环境，安装并启动 TestPilot，从网页创建草稿，分别试本地文件和在线合成文档，保存并解析。普通目录可用于查找规格文件，浏览和解析时 Git 调用数为零。在有 Git 的环境另验已有仓库任务可查看，高级仓库入口可选择 HEAD 和显式范围。文档不可读或无权限时可保留草稿并换来源 |
| P0 · 本地源码目录 | 与接口文档同属首期。新增目录采集分支和独立入口，复用快照、静态适配器和接口清单；先验证普通目录及解压后的交付目录 | 在无 Git 命令、无 `.git`、无提交 ID 的 Windows 环境，选定合成 FastAPI 源码目录，解析出接口并记录相对路径与哈希，浏览和解析期间 Git 调用数为零。验证范围外文件、敏感文件和越界链接未被读取，未支持语言给出明确提示，默认模型材料不含原始源码。原 Git 输入通过回归检查 |
| P1 · 明确资料和执行权限 | 基于 P0，区分有待补齐的资料、范围、环境、账号和审批。按现有状态模型与执行配置展示进度；用可选发布号或工单引用追溯声明信息，将现有提交探针结果与声明信息分别呈现 | 只有文档时可导入并准备待审用例。使用合成回环服务验证匿名与测试账号执行、缺账号时无业务请求、缺审批或更换环境后无业务请求，以及历史批次保留原审批与结果 |
| P2 · 共享测试环境 | P0/P1 可独立交付。确认团队的 QA 接入地址、网络与身份政策，以及能由谁登记和批准后，再设计已登记环境的执行接入。候选为组织管理的执行端，或受登记环境策略约束的直连。方案评审需覆盖服务身份、环境允许列表、账号范围、操作审批、合成数据和报告归属 | 先通过隔离合成服务验证准入、拒绝、变更后重新审批与审计记录，再在明确授权的共享 QA 环境验证。覆盖非登记目标、跨目标跳转、环境或凭据不匹配时的阻断；文档 `servers` 字段不能替用户决定执行目标 |

P0 验收复用 `test_ui_server.py` 中的任务生命周期与文件浏览测试、`test_task_discovery.py` 的快照和 Git 发现测试、`test_openapi_import.py` 的文档发现测试，以及 `test_adapters.py` 的静态提取测试。新增目录与文档路径零 Git 调用、目录采集范围和模型输入的回归检查。用浏览器验证两条普通接入路径从新建任务走到接口清单。P1 复用 `test_task_approval.py` 和 `test_task_execution.py` 验证审批前零请求、范围绑定与凭据缺失。实现后用全新 `--basetemp` 运行相关测试，再运行全量 pytest、Ruff 和 `git diff --check`，按实际结果更新验收。P2 的真实接入须在环境资料、审批人和试点范围确认后进行。
